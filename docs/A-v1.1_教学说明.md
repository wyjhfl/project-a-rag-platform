# A-v1.1 教学说明

## 1. A-v1.1 解决的业务问题

A-v1.1 解决的不是“功能不够多”，而是“功能已经很多，但外部读者不容易判断哪些是真的默认可跑、哪些只是可选增强、哪些已经有证据”。

对一个求职展示型 RAG 项目来说，v1.0 之后最危险的问题通常不是少一个功能，而是下面三类错位：

- README 说得很满，但仓库默认环境并不能直接复现。
- 代码里有增强能力入口，但文档没有说清它们是不是默认能力。
- 面试讲法和真实仓库状态不一致，追问两层就会暴露边界不清。

所以 A-v1.1 的业务目标，是把“能做”升级成“能被别人确认地做”，把“项目故事”升级成“项目证据链”。

## 2. 核心技术点

### 2.1 发布版边界管理

原理：

- 研发仓库经常会先保留很多增强能力、探针、实验脚本和真实联调记录。
- 公开版不能把这些都当成默认承诺，否则环境复杂度会失控。

本项目为什么需要：

- Project A 已经覆盖基础 RAG、混合检索、多轮、工单、评测、Neo4j、Redis、Milvus、多模态等多条线。
- 如果不把“默认主链”和“按需增强”分层，面试时很容易被问成“这些是不是都能直接跑”。

落地模块：

- `README.md`
- `docs/A-v1.0_发布审查文档.md`
- `docs/A-v1.1_面试讲法与版本边界说明.md`

### 2.2 证据链设计

原理：

- 一条可信的工程叙事，至少要能落到“代码入口 + 测试或验收材料 + 边界说明”这三层。
- 只有代码没有材料，外部读者无法快速判断稳定性。
- 只有材料没有代码入口，容易变成宣传稿。

本项目为什么需要：

- 这个仓库已经保留了很多真实验收文档，例如 Redis、PostgreSQL、Neo4j、Milvus / 多模态。
- 如果这些材料在 README、功能核对表、发布审查文档之间没有形成索引闭环，信息会散。

落地模块：

- `docs/A-v1.0_public_feature_audit.md`
- `README.md`
- `docs/A-v1.1_验证记录.md`

### 2.3 默认能力与可选增强分层

原理：

- 默认能力强调“开箱即可复现”。
- 可选增强强调“代码保留、按需接入、可能依赖外部服务或运行环境”。

如果不分层会怎样：

- CI 会被外部依赖绑架。
- 文档会夸大默认能力。
- 面试时会把讨论重点从业务闭环拉偏到环境搭建细节。

本项目为什么需要：

- 当前默认主链是 `SQLite + Chroma + 脱敏资料 + 核心 API + Vue3`。
- Redis、PostgreSQL、Milvus、Neo4j、真实多模态是真实存在的增强项，但它们不该被描述成“所有人零配置都能直接跑”。

落地模块：

- `README.md`
- `docs/A-v1.0_public_feature_audit.md`
- `docs/A-v1.1_面试讲法与版本边界说明.md`

### 2.4 API 对外表达

原理：

- 对外接口说明不能只列路径，还要说明这些接口在主链中的角色。
- 对演示型项目尤其如此，因为面试官或协作者通常会按“调用顺序”理解你的系统。

本项目为什么需要：

- Project A 不是只有 `chat`，还有入库、多轮、工单、评测入口。
- 如果不写最小调用顺序，读者很难快速看懂“这不是一个单接口问答 demo”。

落地模块：

- `README.md`
- `docs/A-v1.1_API与关键演示说明.md`

### 2.5 面试叙事收口

原理：

- 面试讲法不是复述功能清单，而是用“主链、边界、证据、取舍”讲工程判断。
- 项目成熟后，最容易被追问的不是“你会不会做 RAG”，而是“你怎么定义默认能力、怎么做验证、为什么不默认全开所有增强项”。

本项目为什么需要：

- 仓库已经到了可以被追问取舍的阶段。
- 如果继续只讲“我做了很多东西”，反而会削弱可信度。

落地模块：

- `docs/A-v1.1_面试讲法与版本边界说明.md`
- `docs/A-v1.0_发布审查文档.md`

## 3. 为什么 A-v1.1 先补可信度，不先堆功能

因为现在最短板的不是“有没有功能”，而是“外部读者能不能快速确认功能边界和证据”。

继续堆功能的风险：

- 会把主链叙事越做越散。
- 会继续增加 README 和真实状态的不一致风险。
- 会把最适合面试展示的“工程判断”埋掉。

先补可信度的收益：

- 让现有 v1.0 能力更容易被别人读懂、验证和复现。
- 给后续 v1.2 评测与可观测性增强打下统一口径。
- 把“默认可跑”和“真实增强验收”分层固定下来。

## 4. 本版本的最小可运行目标

A-v1.1 的最小目标不是新接口，而是让读者只看仓库文件就能回答下面 5 个问题：

1. 这个项目的正式演示主入口是什么。
2. 默认本地能跑什么，不能默认承诺什么。
3. 每个公开宣称的核心能力对应哪个代码入口。
4. 这些能力的验证材料在哪里。
5. 面试时该怎么诚实地讲边界而不把项目说弱。

## 5. 本版本落到哪些模块

- `README.md`：统一入口、默认能力、证据索引、API 使用顺序。
- `docs/A-v1.0_public_feature_audit.md`：功能项、代码入口、证据、公开策略收口。
- `docs/A-v1.0_发布审查文档.md`：发布基线和边界判断。
- `docs/A-v1.1_面试讲法与版本边界说明.md`：固定对外讲法。
- `docs/A-v1.1_API与关键演示说明.md`：接口、演示顺序、截图对应关系。
- `docs/A-v1.1_验证记录.md`：本轮 A-v1.1 级别复验和截图证据索引。
- `docs/dev_log.md`、`docs/debug_log.md`：沉淀本轮判断过程。

## 6. 面试或协作时可以怎么概括 A-v1.1

可以直接这样讲：

> A-v1.1 没有继续堆功能，而是把公开版的边界、证据和接口说明收紧了。  
> 现在我能明确区分默认主链和可选增强，并且每个核心能力都能落到代码入口和验证材料，不会把研发验证版夸大成默认开箱版。
